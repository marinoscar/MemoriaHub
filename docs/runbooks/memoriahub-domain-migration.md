# Runbook: the MemoriaHub domain schema and its migrations (`@marinoscar/memoriahub-db`)

Use this to change a domain table, to understand the two copies of every domain file, to install the domain into a host that has no MemoriaHub history, and to roll a change back. The package is [packages/memoriahub-db](../../packages/memoriahub-db/README.md); the decision behind the packages is [ADR-0001](../decisions/0001-packages-first.md) (RETRO-J3, #606). The platform's own tables follow the [platform migration procedure](database-baseline.md) and are not covered here.

## 1. What lives where

| What | Owner | Edit it in |
|---|---|---|
| Domain Prisma models (`media_items`, `people`, `memories`, ... 40 tables) | `@marinoscar/memoriahub-db` | `packages/memoriahub-db/schema/memoriahub.<slice>.prisma` |
| Back-relations onto `User`, `Organization`, `Group`, `StorageObject` | the package (`ownership`, `identity` fragments) | the same folder |
| Legacy platform tables (`mh_legacy_*`, the legacy credential tables), the avatar side table `user_profiles`, the app's back-relations | the app | `apps/api/prisma/fragments/*.prisma` (`platform-*.legacy.prisma`, `user-profile.prisma`, `identity-extensions.prisma`) |
| Domain migrations | the package | `packages/memoriahub-db/migrations/<id>/migration.sql`, listed with a sha256 in `migrations/manifest.json` |
| Raw-SQL index list, extension list, functions, triggers, CHECKs | the package | `raw-sql-indexes.json`, `extensions.json`, `schema-objects.json` |

**Two copies.** `memoriahub-db sync` (run by `npm run db:compose`) writes `apps/api/prisma/fragments/memoriahub.<slice>.prisma` (header `// GENERATED by memoriahub-db sync`) and records everything in `apps/api/prisma/memoriahub.lock`. The generated fragment is byte-identical to the package file plus the two header lines; never edit it and never run `prisma format` on it. `platform db compose` then composes the app's `prisma/schema/` from all fragments. `npm run db:check` (`platform db check && memoriahub-db check`) fails on any difference between a copy and the package, on any change to an installed migration (comments inside `migration.sql` count), and on a raw-SQL index missing from `platform.lock`.

## 2. The history policy (RETRO-J3 decision 1)

The web app built the domain through 130 migrations, 37 of them mixed with platform, legacy or since-dropped tables and most written against `circles`, which no longer exists. `node scripts/memoriahub-packages/classify-migrations.mjs` classifies them: 20 touch only domain tables, 63 only platform, legacy or app tables, 37 both, 10 no table (an index or enum statement). The mixed ones are the first domain migrations (`add_media_domain`, `add_family_circles`, ...), the platform retrofit's `i2`, `i4`, `i5`, `c2`, `k2`, the avatar move and the Android and Media Sync tables. The domain-only ones depend on tables the mixed ones create, so no subset of the history runs on an empty host.

Decision: **the package ships one baseline migration, `20261110200000_domain_baseline`**, the whole domain in its final state (30 enums, four functions, 40 tables with constraints, indexes, triggers and row-level-security policies), generated by `scripts/memoriahub-packages/generate-domain-baseline.mjs` from a database migrated with the web app's history. This is the issue's recommended option (a) in a simpler form: there is no catch-up of a partly adopted history to reconcile, because nothing of the history is shipped.

- **The web app adopts it.** `memoriahub-db sync` sees `20260610000000_add_media_domain` in `prisma/migrations` and records the baseline in `memoriahub.lock` as `{ "adopted": true, "installedDir": null }`. No directory is written and no database runs it, so there is **no `prisma migrate resolve`, no deploy step and no change to any database**.
- **A new host installs it** under the `stable` name `20261110200000_memoriahub_domain_baseline` after the platform's migrations.
- **Every later domain migration** is authored in the app, promoted to the package (section 4) and installed under its original name on the web app, under its stable name on a new host.
- **The fresh path is tested against the history path**: `packages/memoriahub-db/test/apply.db.test.ts` builds one database from the platform migrations plus the baseline and one from the web app's whole history and compares every domain column, constraint, index, trigger, RLS policy, enum and function (`scripts/memoriahub-packages/compare-domain-schema.mjs`); `check --database` passes on both.

Decisions on the other two open points: the web app uses `original` names for what it installs later (production `_prisma_migrations` rows carry the original names; fresh hosts use `stable`); `node_backup_*` and `media_sync_*` live in the package (`backup` and `mediasync` slices), because the platform's nodes and Android slices own only `worker_nodes`, `worker_node_events` and the release tables.

## 3. Proving the database did not change (the J3 acceptance)

The adoption changes no migration, writes no migration directory and leaves the composed schema equal. From `apps/api`, with `POSTGRES_*` pointing at a database migrated with `npm run prisma:migrate`:

```bash
npm run db:compose && npm run db:compose:check          # fragments + composed schema up to date
npm run db:check && npm run db:check:database           # platform.lock, memoriahub.lock, extension, 15 raw indexes, 23 triggers
npm run db:memoriahub:check:database
# the composed schema equals main's: no output but "No difference detected"
npx prisma migrate diff --from-schema <main's prisma/schema copy> --to-schema prisma/schema --exit-code
npm run db:drift && npm run db:drift:memoriahub
```

`db:drift` needs a role that may create a database for its shadow replay (or `--shadow-database-url`); its output is the same before and after the move.

## 4. Changing a domain table

1. Edit the model in `packages/memoriahub-db/schema/memoriahub.<slice>.prisma`. A raw-SQL index goes in the migration and in `raw-sql-indexes.json`, never into the fragment as `@@index` or `@@unique`.
2. `cd apps/api && npm run db:compose` (writes the generated copy, recomposes the schema), then `npm run prisma:generate`.
3. `npm run prisma:migrate:dev -- --create-only --name <name>`; review the SQL. A migration may create and change domain tables and may declare a foreign key to a host table (`users`, `organizations`, `groups`, `storage_objects`, `worker_nodes`, `personal_access_tokens`); it may not change a host table (that is the platform's or the app's).
4. `npx memoriahub-db promote <ts>_<name> --id <name> --slice <slice>`: moves the draft into `packages/memoriahub-db/migrations/`, appends it to the manifest with its sha256, installs it into `apps/api/prisma/migrations/` under the same name and records it in `memoriahub.lock`. It refuses a migration that touches a table the domain does not own, an id that sorts before the newest package migration, and warns about a new partial, expression or non-btree index not yet in `raw-sql-indexes.json` (add it with its `pg_indexes.indexdef`, then `memoriahub-db sync` again; for a new function, trigger or CHECK constraint add it to `schema-objects.json`).
5. Apply it (`npm run prisma:migrate`), then `npm run db:check`, `db:check:database`, `db:drift`.
6. Commit the package copy, the app copy, `memoriahub.lock`, `platform.lock` (when an index was added), the generated fragment and a changeset (`@marinoscar/memoriahub-db`). At most one open PR may carry a migration (`migration-lock`).

A data step that moves rows into a platform table (the circles-to-groups import, the share and invite imports) stays an app migration: it is not a domain migration and is never promoted.

## 5. Installing the domain into a host with no MemoriaHub history

```bash
platform db sync --timestamp 2024-01-01T00:00:00Z      # the platform's migrations first
memoriahub-db sync --names stable                      # fragments, the baseline as 20261110200000_memoriahub_domain_baseline, memoriahub.lock
platform db compose
# as a superuser, once: CREATE EXTENSION IF NOT EXISTS vector;   (the package never creates an extension)
prisma migrate deploy
memoriahub-db check --database
```

The host must hold a default organization (`organizations.is_default`) before the first content row is written: `mh_default_org_id()` reads it.

## 6. Failure codes

`memoriahub-db check` prints `CODE  message` lines and exits 1:

| Code | Meaning and fix |
|---|---|
| `FRAGMENT_MISSING`, `FRAGMENT_MODIFIED`, `FRAGMENT_STALE` | a generated fragment is absent, edited or has no package source: `memoriahub-db sync` restores it; edit the package file |
| `LOCK_MISSING`, `NOT_INSTALLED` | `prisma/memoriahub.lock` is absent or lacks a package migration: `memoriahub-db sync` |
| `INSTALLED_MODIFIED` | an installed `migration.sql` differs from the lock: restore it from version control (never edit an installed migration) |
| `LOCK_ENTRY_MISSING` | the lock names a directory that is gone: restore it |
| `LOCK_ENTRY_UNKNOWN`, `LOCK_DIFFERS_FROM_PACKAGE` | the lock and the package disagree (including a changed baseline): a published migration is never edited; fix forward with a new migration |
| `PLATFORM_LOCK_INDEX_MISSING`, `PLATFORM_LOCK_INDEX_DIFFERS` | a package raw-SQL index is missing from, or differs in, `platform.lock`: `memoriahub-db sync` |
| `UNLISTED_RAW_INDEX`, `LISTED_INDEX_NOT_FOUND`, `LISTED_INDEX_MISMATCH`, `FRAGMENT_DECLARES_RAW_INDEX` | the raw-SQL index tripwire: the inventory and the migrations or fragments disagree |
| `EXTENSION_MISSING`, `EXTENSION_TOO_OLD` (`--database`) | ask a superuser for `CREATE EXTENSION IF NOT EXISTS vector;` |
| `INDEX_MISSING`, `TRIGGER_MISSING`, `FUNCTION_MISSING`, `CONSTRAINT_MISSING` (`--database`) | the database lacks an object the package lists |

## 7. Rollback

A change before this PR merges: revert it. After it merged, nothing in a database changed, so reverting the PR (restore the app fragments from git, delete `prisma/memoriahub.lock` and the generated `memoriahub.*.prisma` copies, remove the workspace) is a file-only rollback. A promoted domain migration that was already applied is rolled forward with a new migration, as any applied migration.
