# media

The media core of the MemoriaHub domain, moved onto the host ports slice by slice (RETRO-J5, #613). It carries the upload enrichment fan-out registry, the sidecar touch service, the `upload_completed` producer, the Android Media Sync device service and its controller, the empty-trash run engine (service, two job handlers, controller), the trash purge job, and the `media_items` where-builder.

## Purpose and scope

Everything a media item needs that does not depend on another slice, written against `@marinoscar/memoriahub-api/ports` only (no platform import, no generated database client). The upload fan-out is a registry: tagging, face detection, burst, duplicate, location-inference and social-media slices register their enqueue and its gate with `UploadEnrichmentRegistry.register(type, gate)` instead of `media` importing them, which keeps the dependency one way. `MediaTouchService` bumps `media_items.updated_at` after a related-table write so the node backup change feed sees it. `UploadNotificationService` raises `media.upload_completed` as one rolling 15-minute row per recipient however many files an import registers. `MediaSyncService` is the Android Media Sync device API (register, versioned desired config, commands, check-in, runs, diagnostics) with owner-scoped 404s and PAT scoping. Status: experimental until the first published release.

## Entry point

`@marinoscar/memoriahub-api/media`. It imports the `ports` and `core` slices through their `index.ts` and nothing else of the package.

## Peer dependencies

`@nestjs/common`, `@nestjs/core`, `@nestjs/swagger`, `nestjs-zod`, `zod`, `@opentelemetry/api` (optional: the two empty-trash handlers open spans), `@marinoscar/memoriahub-compute` (the metadata extraction functions and node result schema) and `@marinoscar/memoriahub-contract` (the Media Sync and run wire schemas and refusal reasons).

## Configuration

`MediaModule.forRoot(options)`; the options object is reserved and empty today. Import it once in the host and re-export it from the host's media module (the registry is a singleton). The slice reads no environment variable: a gate that honours a kill switch (`AUTO_TAG_ENABLED`) lives in the registration of the slice that owns the feature.

## Extension-point catalog

`UploadEnrichmentRegistry` is the extension point of the fan-out: a slice calls `register(type, { mediaTypes, order, skipReason, enqueue, onSkipped })` when it starts. `skipReason` answers `null` to enqueue or the logged reason to skip; `onSkipped` is the fallback of a skipped job (video: no social-media detection means face detection runs directly). The registrations run in ascending `order`; the priority of the job each enqueues is the registration's own.


`MEDIA_ITEM_PURGER` (the `MediaItemPurger` interface) is the second: the host binds the batched hard delete of trashed items (rows, stored bytes, grants) that `TrashPurgeHandler` calls, until the gallery service moves into the slice.
**What is in the slice and what is left in the web app.** In the slice: `UploadEnrichmentRegistry` and `UploadEnrichmentService` (fan-out), `MediaTouchService` and `MediaTouchModule`, `UploadNotificationService` (event key `media.upload_completed`, 15-minute window), `MediaThumbnailService` (batched signing, 24 hour URL TTL, cache), `MediaSyncService` (the Media Sync device API: owner-scoped 404, PAT scoping, versioned desired config), `assertMediaSyncSourceDevice`, the `trash_purge` handler and `TrashPurgeTask` (enqueue-only), the `MEDIA_ITEM_PURGER` hook, the empty-trash run engine (`TrashEmptyRunService`, `trash_empty_evaluate` and `trash_empty_execute_batch`, `TrashEmptyRunsController`), `MediaSyncController` with its DTOs, the thumbnail jobs (`ThumbnailRegenHandler`: `thumbnail_regen`, node-eligible with `deriveOutputKey`; `ThumbnailRepairHandler`: the global `thumbnail_repair` sweep, server-only; `ThumbnailRepairTask`: the enqueue-only hourly cron; `ThumbnailNodePersistService`: the persist half of a node's rendering) and the content-addressed thumbnail key convention (`buildThumbnailKey`, issue #434), with three hooks into the host's post-upload processing (`MEDIA_OBJECT_REPROCESSOR`, `MEDIA_THUMBNAIL_PRUNER`, `MEDIA_SYSTEM_ACCESS`: the cross-organization client for the repair scan, bound by the host to its system client under its `media-housekeeping` reason), the metadata re-run (`MetadataExtractionService` and the node-eligible `metadata_extraction` handler, `MetadataBackfillService`, `MetadataController`: `POST /api/media/:id/metadata/rerun` and `GET .../status`, `AdminMetadataController`: `POST /api/admin/metadata/backfill`) with the `MEDIA_REVERSE_GEOCODER` hook (the host binds it to its geo service: the persist half geocodes server-side, a node result never carries a geocode), `MediaMetadataSyncService` (copies the processor metadata of a storage object into the typed columns of its media item; present-only, never nulls, no-clobber of a client content hash, a `P2002` collision retries without the hash) with the `MEDIA_LOCATION_RESOLVER` hook (the host binds it to the location slice's resolver: `location` depends on `media`, so `media` cannot import it), `buildMediaWhere` and the `where*` builders, and the conformance kit. `MediaMetadataSyncService` is provided by the host next to its `storage.object.processed` listener (the event belongs to the host's post-upload pipeline). The controllers are exported classes the host mounts in its own module (the OpenAPI document follows module order); the handlers that need `MEDIA_ITEM_PURGER` are provided by the host too.

Left in `apps/api` (each depends on something that is not in a port yet): the gallery service and controller (`MediaService` with its 13 collaborators: metadata sync, geocode providers, the location-group resolver, the enrichment service and the platform sharing/storage services; 3.6k lines plus the 40 `dto/*` classes), the apply-location helpers and the geocode providers (they move with the location slice), the orientation edit (it calls the host's reprocessor and the AI enhancer's sync-then-prune order), the reprocess controller (the legacy enrichment queue facade and the `Job` row), the thumbnail-rerun controller, the Media Sync device source and doctor checks (they use the platform android-app and doctor slices), `MediaEnrichmentService`'s video post-detection fan-out and per-item rerun helpers, and the notification event declarations (the platform freezes its registries before the Nest container starts, so the events stay declared in `apps/api/src/app-registrations`).

**Security notes.** A non-member of a library is a 404, never a 403 (the access port); Media Sync devices are owner-scoped the same way and a PAT linked to a device reaches only that device. Registration and check-in refuse a session token with `400 PAT_REQUIRED`. Logs carry ids and counts, never a token. Public share links serve the original bytes: EXIF (GPS included) is not stripped. A `BigInt` column leaves the slice as a string; `captured_at` is a civil timestamp rendered in UTC, never in the viewer's zone.
