# media

The media core of the MemoriaHub domain, moved onto the host ports slice by slice (RETRO-J5, #613). It carries the upload enrichment fan-out registry, the sidecar touch service, the `upload_completed` producer, the Android Media Sync device service and its controller, the empty-trash run engine (service, two job handlers, controller), the trash purge job, the metadata and thumbnail jobs, the gallery (`MediaService`, `MediaController`, the request DTOs) and the `media_items` where-builder.

## Purpose and scope

Everything a media item needs that does not depend on another slice, written against `@marinoscar/memoriahub-api/ports` only (no platform import, no generated database client). The upload fan-out is a registry: tagging, face detection, burst, duplicate, location-inference and social-media slices register their enqueue and its gate with `UploadEnrichmentRegistry.register(type, gate)` instead of `media` importing them, which keeps the dependency one way. `MediaTouchService` bumps `media_items.updated_at` after a related-table write so the node backup change feed sees it. `UploadNotificationService` raises `media.upload_completed` as one rolling 15-minute row per recipient however many files an import registers. `MediaSyncService` is the Android Media Sync device API (register, versioned desired config, commands, check-in, runs, diagnostics) with owner-scoped 404s and PAT scoping. Status: experimental until the first published release.

## Entry point

`@marinoscar/memoriahub-api/media`. It imports the `ports` and `core` slices through their `index.ts` and nothing else of the package.

## Peer dependencies

`@nestjs/common`, `@nestjs/core`, `@nestjs/swagger`, `nestjs-zod`, `zod`, `@opentelemetry/api` (optional: the two empty-trash handlers open spans), `@marinoscar/memoriahub-compute` (the metadata extraction functions and node result schema) and `@marinoscar/memoriahub-contract` (the Media Sync and run wire schemas and refusal reasons).

## Configuration

`MediaModule.forRoot(options)`; the options object is reserved and empty today. Import it once in the host and re-export it from the host's media module (the registry is a singleton). The slice reads no environment variable: a gate that honours a kill switch (`AUTO_TAG_ENABLED`) lives in the registration of the slice that owns the feature.

## Extension-point catalog

`MEDIA_RECOVERY_SYSTEM_ACCESS` (a `MediaSystemAccess`) is the extension point the storage recovery jobs reach `storage_objects` across organizations through: the host binds it under its own audit reason, apart from the thumbnail repair sweep's `MEDIA_SYSTEM_ACCESS`.

`UploadEnrichmentRegistry` is the extension point of the fan-out: a slice calls `register(type, { mediaTypes, order, skipReason, enqueue, onSkipped })` when it starts. `skipReason` answers `null` to enqueue or the logged reason to skip; `onSkipped` is the fallback of a skipped job (video: no social-media detection means face detection runs directly). The registrations run in ascending `order`; the priority of the job each enqueues is the registration's own.


`MEDIA_LOCATION_RESOLVER` (`MediaLocationResolver`), `MEDIA_REVERSE_GEOCODER` (`MediaReverseGeocoder`), `MEDIA_OBJECT_REPROCESSOR` (`MediaObjectReprocessor`), `MEDIA_THUMBNAIL_PRUNER` (`MediaThumbnailPruner`) and `MEDIA_SYSTEM_ACCESS` (`MediaSystemAccess`) are the hooks into what the host or a slice that depends on `media` owns: the canonical-name resolver of the location slice (`location` depends on `media`, so `media` cannot import it), reverse geocoding with the deployment's provider and credential, re-running the post-upload processors for one object, pruning superseded thumbnails (reprocess, then await the media item sync, then prune: issue #434) and the cross-organization client for the global thumbnail repair scan. The host binds each token once.

`MEDIA_ITEM_PURGER` (the `MediaItemPurger` interface) is the second: the host binds it (to `MediaService`) for the batched hard delete of trashed items (rows, stored bytes, grants) that `TrashPurgeHandler` calls.
`MEDIA_GEO_LOCATION_PROVIDER` (`MediaGeoLocationProvider`), `MEDIA_FORWARD_GEOCODER` (`MediaForwardGeocoder`), `MEDIA_ENRICHMENT` (`MediaEnrichment`), `MEDIA_WEBHOOK_EVENTS` (`MediaWebhookEvents`) and `MEDIA_CSV_STRINGIFIER` (`MediaCsvStringifier`) are the hooks of the gallery service: reverse geocoding with the deployment provider, place search, the upload-time and rerun enrichment jobs, the outbound media webhooks (optional) and the streaming CSV writer of the export (optional). The host binds each token once.

**The gallery (RETRO-J5, #613).** `MediaService` and `MediaController` (`/api/media`) with the 28 request DTO classes (`MediaQueryDto`, `CreateMediaDto`, the album, bulk, trash, locations, dashboard and geocode queries) live in `gallery/` and `dto/`. The service registers an uploaded storage object as a media item (content-hash dedup: a pre-check plus the `P2002` race), lists the gallery in two modes selected by the presence of `page` (keyset over `media_items_gallery_idx`, no `COUNT(*)`, or the legacy offset mode with its count), serves the albums, tags, map points and server-side clusters, the explore and places tiers (canonical-or-raw location names), archive and trash, the bulk actions, the NDJSON/CSV export, the review-queue counts and the batched hard delete (`purgeMediaItemsBatched`, which is also the `MEDIA_ITEM_PURGER` the trash jobs call). It reaches the database (`MEMORIAHUB_PRISMA`), the access policy (`MEMORIAHUB_ACCESS`: the owner-scope check first, then a record grant for a refused caller, and the grants of a hard-deleted row), the object store (`MEMORIAHUB_OBJECT_STORE`: the active store for a redundant upload, the recorded store for signing and deleting) and the metrics (`MEMORIAHUB_METRICS`: `mediaUploads`, `mediaUploadSize`, `mediaTagsApplied`) through the `ports` slice, and the geocoders, the enrichment fan-out helpers, the outbound webhooks and the CSV writer through five hooks: `MEDIA_GEO_LOCATION_PROVIDER` (reverse geocoding with the deployment provider), `MEDIA_FORWARD_GEOCODER` (place search), `MEDIA_ENRICHMENT` (upload-time jobs and the per-item reruns), `MEDIA_WEBHOOK_EVENTS` (optional: `media.item.created`, `.trashed`, `.deleted` and `media.upload.completed`) and `MEDIA_CSV_STRINGIFIER` (optional: the CSV export answers 503 without it). The `media` to `location` cycle is broken downwards: `fold`, `GEO_CLEAR_COLUMNS`, `geoResultToMediaColumns` and `applyLocation` live in `media` (over `MEDIA_LOCATION_RESOLVER` and `MEDIA_GEO_LOCATION_PROVIDER`) and `location` re-exports them. A `P2002` is read structurally (`code === 'P2002'`), `Prisma.sql/raw/join/JsonNull` come from `core`, and the controller is an exported class over `@MemoriahubAuth` that the host mounts in its own module (the OpenAPI document follows module order; `@Res()` takes the structural `MediaReply`).

**What is in the slice and what is left in the web app.** In the slice: `UploadEnrichmentRegistry` and `UploadEnrichmentService` (fan-out), `MediaTouchService` and `MediaTouchModule`, `UploadNotificationService` (event key `media.upload_completed`, 15-minute window), `MediaThumbnailService` (batched signing, 24 hour URL TTL, cache), `MediaSyncService` (the Media Sync device API: owner-scoped 404, PAT scoping, versioned desired config), `assertMediaSyncSourceDevice`, the `trash_purge` handler and `TrashPurgeTask` (enqueue-only), the `MEDIA_ITEM_PURGER` hook, the empty-trash run engine (`TrashEmptyRunService`, `trash_empty_evaluate` and `trash_empty_execute_batch`, `TrashEmptyRunsController`), `MediaSyncController` with its DTOs, the thumbnail jobs (`ThumbnailRegenHandler`: `thumbnail_regen`, node-eligible with `deriveOutputKey`; `ThumbnailRepairHandler`: the global `thumbnail_repair` sweep, server-only; `ThumbnailRepairTask`: the enqueue-only hourly cron; `ThumbnailNodePersistService`: the persist half of a node's rendering) and the content-addressed thumbnail key convention (`buildThumbnailKey`, issue #434), with three hooks into the host's post-upload processing (`MEDIA_OBJECT_REPROCESSOR`, `MEDIA_THUMBNAIL_PRUNER`, `MEDIA_SYSTEM_ACCESS`: the cross-organization client for the repair scan, bound by the host to its system client under its `media-housekeeping` reason), the metadata re-run (`MetadataExtractionService` and the node-eligible `metadata_extraction` handler, `MetadataBackfillService`, `MetadataController`: `POST /api/media/:id/metadata/rerun` and `GET .../status`, `AdminMetadataController`: `POST /api/admin/metadata/backfill`) with the `MEDIA_REVERSE_GEOCODER` hook (the host binds it to its geo service: the persist half geocodes server-side, a node result never carries a geocode), `MediaMetadataSyncService` (copies the processor metadata of a storage object into the typed columns of its media item; present-only, never nulls, no-clobber of a client content hash, a `P2002` collision retries without the hash) with the `MEDIA_LOCATION_RESOLVER` hook (the host binds it to the location slice's resolver), the gallery (`MediaService`, `MediaController` and the DTOs, above), `buildMediaWhere` and the `where*` builders, and the conformance kit. `MediaMetadataSyncService` and `MediaService` are provided by the host (the first next to its `storage.object.processed` listener, which belongs to the host's post-upload pipeline; the second beside the five gallery hooks it binds). The controllers are exported classes the host mounts in its own module (the OpenAPI document follows module order); the handlers that need `MEDIA_ITEM_PURGER` are provided by the host too.

**The review-queue notifications (epic #240, RETRO-C9 #612, RETRO-J10 #624).** `ReviewQueueReconcileService` keeps ONE live notification row per (user, library, review-queue event) in step with the pending count: `reconcileAll` reads the `features` namespace once, visits every library (`allScopes`), asks `MediaService.computeReviewCounts` once per library and writes one `notifyState` per eligible member (collaborators and library admins: `membersOf(id, ['admin', 'editor'])`) and queue with a pending count; a count of 0, a disabled queue or a member who can no longer act drains the row (`notifyState` with `count: 0`, the live rows listed by the optional `liveStates` of the notify port). The four event keys (`REVIEW_QUEUE_EVENT_KEYS`: `review.bursts`, `review.duplicates`, `review.location_suggestions`, `review.enhancements`) and the job type `notifications.review_queue_reconcile` (`REVIEW_QUEUE_RECONCILE_TYPE`; server-only, a system job, 15 minutes, three attempts) are permanent. `ReviewQueueReconcileHandler` runs it; `ReviewQueueReconcileTask` is the enqueue-only hourly cron (`NOTIFICATIONS_RECONCILE_ENABLED=false` turns it off). The host lists the three as providers and declares the four events (titles, links, `STATE` folding) in its own notification registry: the platform freezes its registries before the Nest container starts, so an event cannot be declared through the notify port from a provider. Without `liveStates` the sweep writes the counts but cannot drain.

**The permanent-failure notification (epic #240, issue #247, RETRO-J10 #624).** `EnrichmentFailureNotificationListener` subscribes to the jobs port's `onSettled` and, for a job that failed for good (`status: 'failed'`: a retry or a rate-limit deferral settles nothing), raises `media.enrichment_failed` (`ENRICHMENT_FAILED_EVENT_KEY`, permanent) for every administrator the optional `adminUserIds` of the identity port names, as ONE `notifyCounted` row per (administrator, job type) with no window (`match: { jobType }`, `lastError` cut to 500 characters). A poison-pill batch of 400 failures is one row with `count: 400`. A host that does not bind `adminUserIds` skips it. The host lists the listener as a provider and declares the event in its notification registry.

**The storage recovery jobs (RETRO-D1b #567, RETRO-J5 #613).** `StorageRecoveryHandler` (`media.storage.recover_stuck`: mode `stuck` re-queues objects orphaned at `processing` past `STORAGE_PROCESSING_STUCK_MINUTES`, capped at `STORAGE_PROCESSING_MAX_RETRIES` with the counter persisted before the enqueue; mode `failed` re-queues failed image objects), `StorageReprocessHandler` (`media.storage.reprocess`: the ready or failed media objects of one library or of every library, at background priority 100), `StorageRecoveryService` (the keyset scans; per object it queues the host's `storage.object.process` job in the object's organization with the payload `{ objectId, orgId }`) and `StorageRecoveryTask` (the enqueue-only ten-minute cron; `STORAGE_PROCESSING_STUCK_RESET_ENABLED=false` turns it off). Both jobs are system jobs and server-only (no node pair), 10 and 30 minute profiles, three attempts. They reach `storage_objects` across organizations through the `MEDIA_RECOVERY_SYSTEM_ACCESS` hook (a `MediaSystemAccess` the host binds under its own audit reason, apart from the thumbnail repair sweep's `MEDIA_SYSTEM_ACCESS`); the host lists the handlers, the service and the task as providers.

**The enrichment service (RETRO-J5, #613).** `MediaEnrichmentService` is the packaged `MEDIA_ENRICHMENT` hook (`forRoot()` binds the token to it) and the class the host binds the social-media slice's `SOCIAL_MEDIA_POST_DETECTION` hook to: `enqueueUploadEnrichment` (the registry fan-out), `enqueueVideoPostDetectionEnrichment` (the video fan-out withheld while social-media detection classifies a video: `video_face_detection` behind `features.faceRecognition`, `face.video.enabled` and `FACE_AUTO_DETECT`, `video_auto_tagging` behind `features.autoTagging`, `autoTagging.video.enabled` and `AUTO_TAG_ENABLED`; priority rerun 0, upload 20, backfill 100), the per-item rerun helpers (`enqueueTagRerun`, `enqueueFaceRerun`, `enqueueThumbnailRerun`: priority 0, reason `rerun`, status `pending`, no feature check) and `enqueueForStorageObject` (the backstop the host's `OBJECT_PROCESSED_EVENT` listener calls). It reads `features`, `face` and `autoTagging` through the settings port and enqueues through the jobs port with the media-item subject convention.

**The recovery and edit routes (RETRO-J10, #624).** `MediaOrientationEditService` and `MediaOrientationEditController` (`POST /api/media/:id/edit/orientation`: the destructive rotate or flip, then the host reprocessor, the awaited metadata sync and the prune of the superseded thumbnail in that order, then a best-effort face re-queue; the service is provided by the host because it needs the two post-upload hooks), `MediaThumbnailRerunController` (`POST /api/media/:id/thumbnail/rerun`, synchronous through `MEDIA_OBJECT_REPROCESSOR`) and `MediaReprocessController` with its three body DTO classes (`/api/admin/media/reprocess`, `reprocess-stuck`, `reprocess-failed`, `thumbnails/repair`: each only enqueues a job through the jobs port and reports the row's status; the two `media.storage.*` type strings are `STORAGE_RECOVER_STUCK_TYPE` and `STORAGE_REPROCESS_TYPE`, permanent, and the host registers their handlers). The three controllers are exported classes over `@MemoriahubAuth` that the host mounts. The geocode providers and the forward geocoder moved to the location slice (they are bound through the hooks above).

**The `android.media-sync` check (RETRO-J10, #624).** `AndroidMediaSyncDoctorCheck` (`memoriahub.android.media-sync`, category `android`) warns about an active device silent for more than 48 hours, with blocked files, without full media permission or with a revoked or expired token; it registers through `MEMORIAHUB_DOCTOR` from `forRoot()` and reads `media_sync_devices` and the paired tokens through the database port. The troubleshooting table in `docs/runbooks/android-app.md` is unchanged (id, thresholds and statuses are the ones it names).

**The Media Sync device source (RETRO-J5, #613).** `mediaSyncReportedApps` and `mediaSyncDevicesBehind` are the two queries the host's Android app slice asks of its one native capability (the (package, signer) pairs active devices report, and how many run an older build of the current release's package), over `MediaModels.mediaSyncDevice`. The host keeps only the registry entry (`registerAndroidDeviceSource`, permanent id `media-sync`) and the late-bound client, because the registry belongs to the platform.

Left in `apps/api` (each depends on something that is not in a port yet): `android.upload-path` (it reads the active storage provider's capabilities, which the object-store port does not carry) the notification event declarations (the platform freezes its registries before the Nest container starts, so the events stay declared in `apps/api/src/notifications-registry`), and the other producers that need a platform service (`workflow_run_completed`, `enrichment_failed`, `shares.expiring`).

**Security notes.** A non-member of a library is a 404, never a 403 (the access port); Media Sync devices are owner-scoped the same way and a PAT linked to a device reaches only that device. Registration and check-in refuse a session token with `400 PAT_REQUIRED`. Logs carry ids and counts, never a token. Public share links serve the original bytes: EXIF (GPS included) is not stripped. A `BigInt` column leaves the slice as a string; `captured_at` is a civil timestamp rendered in UTC, never in the viewer's zone.
